# Marla 文档入口

这套文档按“事实类型”管理，而不是把所有内容都塞进某个版本目录。目标是让项目所有者能够持续记录想法，同时让新 Agent 在有限上下文内准确施工一个任务。

## 从哪里开始

每次开始工作按以下顺序读取：

1. 根目录 `AGENTS.md`：项目边界、工作纪律和验证要求。
2. 实时 Git 上下文：当前工作树根目录、分支、`HEAD` 和未提交修改。
3. `development/STATUS.md`：整合目标分支已经集成、验证的产品状态和已知风险。
4. 当前开发对话/工作树明确分配的 `tasks/TASK-xxx-*.md`；可选的 `.marla/worktree-state.md` 只能帮助定位 Task，使用前必须与实时 Git 核对。
5. Task 的 `Required Reading`，再检查相关代码和测试。
6. 仅在涉及长期决策时读取或新增相关 ADR。

`STATUS.md` 不登记每个并行功能工作树。没有明确分配的 tracked Task 时，不得从想法池、Backlog 或 Roadmap 自行选择并开始实现。

UI/UX 工作的 skill 路由和使用示例见 [`development/UI_UX_SKILLS.md`](development/UI_UX_SKILLS.md)。

## 文档分层

| 目录或文件 | 回答的问题 | 何时更新 |
| --- | --- | --- |
| `product/` | Marla 是什么，体验原则是什么？ | 产品定位或长期原则改变时 |
| `features/` | 某项功能应如何工作？ | 功能行为或验收标准改变时 |
| `architecture/` | 系统如何分层，数据如何流动？ | 架构事实或接口契约改变时 |
| `architecture/decisions/` | 为什么做出长期决策？ | 只有形成或推翻耐久决策时 |
| `development/STATUS.md` | 整合目标当前实际做到哪里？ | 功能合入并完成目标分支验证，或集成状态明显变化时 |
| `tasks/` | 每个开发对话/工作树被授权做什么？ | 任务创建、推进、工作树验证、整合和关闭时 |
| `development/VERIFICATION.md` | 当前开发基线有哪些实机验收和性能证据？ | 验证项开始、完成或发现缺陷时 |
| `development/VERSIONING.md` | 何时分配版本、建立发布合同和提升版本号？ | 发布阶段或版本策略改变时 |
| `backlog/BACKLOG.md` | 哪些工作已经确定要做，但还没排成当前任务？ | 工作被确认、排序或提升为任务时 |
| `backlog/IDEAS.md` | 讨论过哪些未来可能性，还有什么没想清楚？ | 讨论产生新信息时 |
| `development/ROADMAP.md` | 重要能力按什么大致顺序演进？ | 大阶段顺序或范围改变时 |
| `versions/` | 活动或撤回的发布合同是什么？ | 只有显式发布准备、发布范围改变或合同撤回时 |
| `releases/` | 某个版本最终交付了什么？ | 发布准备或发布完成时 |

## 工作流

```text
讨论中的新功能
  -> IDEAS：完整记录，但没有开发承诺
  -> BACKLOG：产品所有者确认未来要做
  -> 主工作树分配 Task ID，并创建独立分支/工作树
  -> TASK：一次开发对话对应一个持续更新的施工单
       -> Active：功能工作树按路径所有权施工
       -> Ready for integration：功能工作树验证通过
       -> 主工作树审查、合并并验证 main
       -> Done：主线验证和全局文档同步完成
当前开发基线的实现与验证
  -> VERIFICATION：实机验收、性能和内存测量
  -> TASK：验证发现可复现代码缺陷时再创建修复任务
       -> 对话中追加需求：补充范围、验收和变更记录
  -> 代码、测试、相关规格同步修改
  -> STATUS：只保留当前事实和下一步
  -> 项目所有者明确启动发布准备
  -> VERSION CONTRACT：此时才选择版本并建立发布范围与验收
  -> RELEASE：实际发布时汇总结果
```

仍然开放的想法可以长期留在 `IDEAS.md`，不需要为了“整洁”而仓促决定；已经实现、拒绝或被后续工作取代的条目则从当前想法池移除，由 Task、ADR、规格和 Git 历史保存。只有产品所有者明确确认，或已有 Accepted ADR 明确要求实现的未来产品工作，才能进入 Backlog；已经完成或关闭的条目同样不继续占据当前 Backlog。当前开发基线的测试、实机验收和性能测量进入 `VERIFICATION.md`：当前待验证项与已关闭证据必须分开，完成项不能继续表现为待办。开始实现前，由主工作树的整合负责人分配唯一 Task ID、创建命名分支/工作树并提交初始 Task；同一对话中追加的相关功能、修复和配套工作继续写入这个 Task，而不是拆出一串零碎任务。一个工作树通常只有一个写入型 `Active` Task；仓库可以通过显式隔离的工作树并行多个 Task。孵化期没有活动发布合同；首次发布和后续版本都只在项目所有者明确启动发布准备时分配，详见 [`development/VERSIONING.md`](development/VERSIONING.md)。

## 真相优先级

1. 当前工作树的实时代码和自动化测试描述当前行为。
2. 当前工作树被分配的 Task 描述本轮允许修改的范围和完成条件。
3. `STATUS.md` 汇总整合目标已经集成、验证的开发状态与缺口。
4. 产品、架构与功能规格描述更广泛设计。
5. Accepted ADR 描述耐久意图。
6. `STATUS.md` 指向的活动发布合同（若有）描述发布目标，不自动证明已经实现。
7. 版本策略描述发布合同与版本号的生命周期；撤回草案不约束当前开发。
8. Backlog、Ideas 和 Roadmap 描述未来，不证明功能已经实现。

如果这些来源冲突，功能工作树先在当前 Task 中记录差异，再有意识地解决；只有差异进入整合基线后，主工作树才更新 `STATUS.md`。不得静默选择最方便的一份。

## 维护原则

- `STATUS.md` 不写聊天流水账，也不充当所有并行 Task 的活动注册表；历史由 Git 和 tracked Task 保存。
- Task 以一次开发对话为边界，是可以演进的施工记录；对话中每次追加范围都要同步验收和验证要求。
- 主工作树独占本地 `main` 并负责 Task-ID 分配、整合、主线验证、全局文档和授权推送；普通功能实现使用独立 Task 分支/工作树。
- 功能工作树通过本地验证后标记 `Ready for integration`；只有合入目标分支并完成目标分支验证后才能标记 `Done`。
- 只有在新增内容明显无关、需要独立授权、存在重大架构风险或必须并行隔离时，才建议由项目所有者拆成后续 Task。
- 较大的多文件文档工作优先评估由当前工作树的主 Agent 拆成互不重叠的子 Agent 工作并行完成；该 Agent 维护本 Task 和分支内容，主工作树整合负责人维护 `STATUS.md` 并完成全局文档、术语和最终验收核对。
- Ideas 记录上下文和未知项，不写成营销愿望清单。
- Backlog 只写已确认工作，并给出进入 Task 的条件。
- 版本文档中的中英文必须在同一次修改中同步；中文发生冲突时为规范文本。
- 代码行为变化时同步功能规格；架构选择变化时评估 ADR；仅排序变化时更新 Roadmap。
