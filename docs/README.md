# Marla 文档入口

这套文档按“事实类型”管理，而不是把所有内容都塞进某个版本目录。目标是让项目所有者能够持续记录想法，同时让新 Agent 在有限上下文内准确施工一个任务。

## 从哪里开始

每次开始工作按以下顺序读取：

1. 根目录 `AGENTS.md`：项目边界、工作纪律和验证要求。
2. `development/STATUS.md`：当前目标分支已集成的产品状态、缺口和风险。
3. 当前工作树的 `.marla/worktree-state.md`（如果存在），并核对其中的工作树、分支和 Task。
4. 当前对话或本地状态指定的 `tasks/TASK-xxx-*.md`；没有适用 Task 时不得自行从想法池挑选功能开发。
5. 任务施工单的 `Required Reading`，再检查相关代码和测试。
6. 仅在涉及长期决策时读取或新增相关 ADR。

## 文档分层

| 目录或文件 | 回答的问题 | 何时更新 |
| --- | --- | --- |
| `product/` | Marla 是什么，体验原则是什么？ | 产品定位或长期原则改变时 |
| `features/` | 某项功能应如何工作？ | 功能行为或验收标准改变时 |
| `architecture/` | 系统如何分层，数据如何流动？ | 架构事实或接口契约改变时 |
| `architecture/decisions/` | 为什么做出长期决策？ | 只有形成或推翻耐久决策时 |
| `development/STATUS.md` | 目标分支已经集成并验证了什么？ | 整合任务或主线状态明显变化时 |
| `development/WORKTREE_STATE_TEMPLATE.md` | 每个工作树如何指向自己的当前 Task？ | 本地协调字段或恢复规则改变时 |
| `tasks/` | 某次开发对话/工作树获准做什么？ | 任务创建、推进、交接、整合和关闭时 |
| `backlog/BACKLOG.md` | 哪些工作已经确定要做，但还没排成当前任务？ | 工作被确认、排序或提升为任务时 |
| `backlog/IDEAS.md` | 讨论过哪些未来可能性，还有什么没想清楚？ | 讨论产生新信息时 |
| `development/ROADMAP.md` | 重要能力按什么大致顺序演进？ | 大阶段顺序或范围改变时 |
| `versions/` | 当前版本的范围和验收合同是什么？ | 发布合同改变时；不记录日常进度 |
| `releases/` | 某个版本最终交付了什么？ | 发布准备或发布完成时 |

## 工作流

```text
讨论中的想法
  -> IDEAS：完整记录，但没有开发承诺
  -> BACKLOG：产品所有者确认要做
  -> TASK：一次开发对话对应一个持续更新、受 Git 管理的施工单
       -> 对话中追加需求：补充范围、验收和变更记录
       -> 独立工作树验证完成：Ready for integration
  -> 代码、测试、相关规格同步修改
  -> 整合负责人合并并验证目标分支
  -> STATUS：只保留已集成事实和下一步
  -> RELEASE：发布时汇总结果
```

想法可以长期留在 `IDEAS.md`，不需要为了“整洁”而仓促决定。只有产品所有者明确确认，或已有 Accepted ADR 明确要求实现的工作，才能进入 Backlog。开始开发对话时创建一个 Task；同一对话中追加的相关功能、修复和配套工作继续写入这个 Task，而不是拆出一串零碎任务。一个共享工作树中通常只有一个写入型 Task；整个仓库允许多个显式隔离的工作树 Task，并通过各自被忽略的 `.marla/worktree-state.md` 协调，不通过 `STATUS.md` 抢占全局槽位。

## 真相优先级

1. 实时代码和自动化测试描述当前行为。
2. 当前对话/工作树对应的 Task 描述本轮允许修改的范围和完成条件。
3. `STATUS.md` 汇总目标分支已经集成、验证的开发状态与缺口。
4. 产品、架构与功能规格描述更广泛设计。
5. Accepted ADR 描述耐久意图。
6. 当前发布合同描述目标，不自动证明已经实现。
7. Backlog、Ideas 和 Roadmap 描述未来，不证明功能已经实现。

如果这些来源冲突，先在当前 Task 记录工作树差异；只有整合后的事实才能写进 `STATUS.md`。不得静默选择最方便的一份。

## 维护原则

- `STATUS.md` 不写聊天流水账、未合并分支进度或全仓 Active Task 列表，历史由 Git 和各 Task 保存。
- Task 以一次开发对话为边界，是可以演进的施工记录；对话中每次追加范围都要同步验收和验证要求。
- 并行 Task ID 由协调者集中预留；功能工作树进入 `Ready for integration` 后，由整合负责人更新 Status、Backlog 和索引并完成 `Done` 验证。
- `.marla/worktree-state.md` 只保存当前工作树的本地协调指针，不提交，也不承载唯一的范围、决定或证据。
- 只有在新增内容明显无关、需要独立授权、存在重大架构风险或必须并行隔离时，才建议由项目所有者拆成后续 Task。
- 较大的多文件文档工作优先评估由主 Agent 拆成互不重叠的子 Agent 工作并行完成；工作树主 Agent 维护 Task，整合负责人统一维护 Status、索引、术语和最终验收。
- Ideas 记录上下文和未知项，不写成营销愿望清单。
- Backlog 只写已确认工作，并给出进入 Task 的条件。
- 版本文档中的中英文必须在同一次修改中同步；中文发生冲突时为规范文本。
- 代码行为变化时同步功能规格；架构选择变化时评估 ADR；仅排序变化时更新 Roadmap。
