# Marla 想法池

这里保存讨论过程中值得继续思考、但尚未形成当前开发承诺的内容。记录得足够详细，是为了几个月后仍能恢复当时的问题、权衡和未知项，而不是让 Agent 看见标题就自行实现。

## 状态定义

- `Captured`：已记录，尚未系统验证。
- `Exploring`：正在比较方案或收集证据。
- `Accepted direction`：长期方向已有 Accepted ADR 或明确产品决定，但尚未排成 Task。
- `Promoted`：已进入 Backlog 或 Task，想法条目保留上下文。
- `Rejected`：决定不做，必须记录原因。
- `Superseded`：被另一条想法或决策替代。

`Priority: Unranked` 是正常状态。想法的价值、成熟度和开发顺序是三件不同的事。

## IDEA-001：按需上下文感知翻译

Status: Accepted direction

Priority: Unranked

Source: 用户讨论 + ADR-0003

Created: 2026-08-05

Related: `ADR-0003-context-engine.md`、BL-005、`DATA_CONTRACTS.md`

### 一句话描述

只在用户触发翻译时，取得最少且有界的应用/附近文字/术语线索，帮助模型理解当前语境，例如在终端中优先采用 IT 语义。

### 用户问题与价值

同一个词在终端、邮件、论文和聊天中的含义与语气可能完全不同。只有被选中的短句往往缺少主语、领域和专有名词信息。适量语境可以减少术语误译和风格漂移，同时不能把 Marla 变成持续观察屏幕的后台监控器。

### 典型场景

- Terminal 中的 `port`、`shell`、`commit` 应优先理解为技术语义。
- 邮件或聊天中要保持礼貌程度和对话人称。
- 代码编辑器中的错误消息应保留标识符、路径和命令参数。
- 同一窗口中连续翻译同一主题时，希望术语一致。

### 当前设想

触发翻译时构造一次短生命周期 `ContextSnapshot`。证据按强弱排序：用户显式术语表 > 有界附近文本 > 当前内容类型 > 应用类别。Bundle ID 或应用名只能作为弱提示，不能单独决定翻译风格。上下文在本地裁剪、清洗后才可能随源文本发送，并在很短时间后丢弃。

### 可能方案与权衡

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 只按应用分类 | 快、数据少、易解释 | 粗糙；终端里也可能阅读自然语言 |
| 读取选区前后有限字符 | 语义信息强 | Accessibility 兼容复杂，可能包含敏感内容 |
| 短时窗口级术语缓存 | 连续翻译一致 | 需要过期、窗口身份和内存边界 |
| 用户手动选择领域 | 隐私清楚、可控 | 增加操作，破坏瞬时体验 |
| 混合策略 | 可按风险渐进增强 | 规则和 UI 解释更复杂 |

### 隐私、安全与可解释性

- 默认不得持续截屏、后台 OCR 或记录完整窗口。
- 必须明确展示“本次将发送什么”，并允许全局关闭或按应用禁用。
- 窗口标题、用户名、路径、密钥样式内容需单独决定是否永不发送或先清洗。
- Provider 请求日志不得记录上下文正文。
- 用户应能区分本地分类与真正发送给云端的文本。

### 性能和内存影响

上下文获取不能推迟结果卡片壳层出现。应设置严格字符数、节点遍历、缓存数量和 TTL 上限；获取失败时直接退化为当前无上下文翻译。不能为了语境常驻大模型。

### 风险与未知

- 额外上下文不一定提升质量，噪声可能反而误导模型。
- Accessibility 对 Electron/Web 内容的附近文本读取差异较大。
- 如何验证“翻译变好”需要稳定样本集和盲测方法。
- 不同 Provider 的提示词遵循程度不同，Qwen-MT 等专用协议未必接受同样上下文字段。

### 进入开发的条件

1. 明确默认关闭还是默认开启，以及用户可见的隐私披露。
2. 定义允许采集和禁止采集的字段、最大字符数、TTL 和清洗规则。
3. 建立至少覆盖终端、网页、邮件、代码错误的质量基准。
4. 定义 Provider 不支持上下文时的降级。
5. 从 BL-005 拆出一个只验证一种证据源的 Task，不一次实现全部缓存。

### 尚未决定

- 是否允许窗口标题进入本地分类，是否永不发送。
- 是否按应用记住用户的语境开关。
- 用户显式术语表与自动短时术语的优先级和展示方式。

### 下一步

先设计隐私边界和离线质量评测样本，不修改 0.1.0 网络请求。

## IDEA-002：原位流式覆盖翻译

Status: Exploring

Priority: Unranked

Source: 用户讨论

Created: 2026-08-05

Related: `UX_PRINCIPLES.md`、`features/inline-translation.md`

### 一句话描述

用户划词后按快捷键或重按触控板，在原文字所在位置出现覆盖层，并在原位流式显示译文；它与“悬停翻译”合并为同一个瞬时入口概念。

### 用户问题与价值

附近卡片仍要求视线从原句移动到卡片。真正的原位翻译可以把上下文切换压到最低，尤其适合网页段落、应用界面和短句。但它并不是普通悬浮卡片换个坐标，而是需要重建原文字的几何、背景和滚动生命周期。

### 预期交互

1. 用户选中文字。
2. 使用快捷键或可选 Force Touch 触发。
3. 覆盖层在原选区稳定出现，先显示等待状态，再流式填充译文。
4. 可临时查看原文/译文对照、复制或关闭。
5. 滚动、窗口移动、内容变化或几何失真时诚实退化到附近卡片。

### 实现难点

- Accessibility 常只给整个选区矩形，不提供每一行和字形的准确形状。
- 译文长度不同，无法保证塞回原面积；需要扩展、滚动或压缩策略。
- 原背景可能包含图片、渐变、链接、选中高亮和动态内容。
- 源应用滚动或重排时必须跟踪坐标，不能覆盖错误位置。
- 非激活窗口要处理鼠标命中、文本选择、键盘 Esc 和源应用焦点。
- Retina、多屏缩放和不同坐标系放大任何几何误差。

### 可能方案与权衡

| 方案 | 适合场景 | 代价 |
| --- | --- | --- |
| 整块矩形覆盖 | 单行/短段落 | 多行形状不准，遮住相邻内容 |
| 每行多个覆盖块 | 网页正文 | 依赖逐行几何，兼容性难 |
| 截取原区域作为背景再覆盖文字 | 复杂背景 | 容易陈旧，涉及屏幕捕获权限 |
| 浏览器扩展/DOM 重写 | 浏览器内精确 | 不通用，形成第二套架构 |
| 附近卡片自动降级 | 所有场景可用 | 体验不总是“原位” |

### 隐私与性能影响

若使用区域截图拟合背景，必须明确它只在内存存在且不上传。持续跟踪窗口可能增加 Accessibility 查询、CPU 和能耗；流式更新不能每个 token 重算整个几何。

### 风险与未知

- 是否能用公共 API 在足够多应用中取得可接受的行几何。
- 原位覆盖会不会妨碍用户继续选择、点击链接或滚动。
- 译文较长时，何种退化最不打断工作。
- 视觉上“像原文”与清楚表明这是 Marla 覆盖层之间如何平衡。

### 进入开发的条件

1. 先做只覆盖单行静态文本的技术原型，不接入正式入口。
2. 定义支持矩阵和必须退化的条件。
3. 证明不会修改源应用内容，也不会误覆盖其他窗口。
4. 用真实 Safari、TextEdit、Terminal 和 Electron 应用验证几何。
5. 形成新的产品/架构决策；0.1.0 继续使用附近卡片。

### 下一步

未来创建独立 feasibility Task，比较“整块覆盖 + 自动降级”和“逐行覆盖”两种最小原型。

## IDEA-003：GLM-OCR 结构化截图翻译

Status: Accepted direction

Priority: Unranked

Source: 用户讨论 + ADR-0002/ADR-0005

Created: 2026-08-05

Related: BL-006、ADR-0002、ADR-0005

### 一句话描述

对表格、代码块或复杂页面截图，可选地调用云端 GLM-OCR 输出 Markdown 或结构化内容，再交给翻译模型并保留布局关系。

### 用户问题与价值

macOS Vision 很适合小段纯文本，但只提供文字与行顺序；截到表格、公式或复杂排版时，纯文本会丢失列关系。GLM-OCR 这类视觉模型可能在无需把本地中档模型常驻内存的前提下恢复结构。

### 当前判断

对于 Marla 首期的小区域截图，中档本地模型处在尴尬位置：比 Vision 更重，却未必接近云端结构模型。因此 0.1.0 只用 Vision；复杂结构作为用户明确选择或自动建议的云端增强，延后到核心交互稳定之后。

### 可能产品形态

- `本地快速`：始终使用 Vision，只发送文字。
- `结构增强`：明确提示会上传选中图片，再调用 GLM-OCR。
- 自动建议但不自动上传：Vision 检测疑似表格后，让用户选择是否结构增强。
- 文档工作区默认采用结构 OCR；瞬时截图入口仍默认 Vision。

### 数据与接口需求

需要定义结构块 ID、类型、层级、边界、阅读顺序、Markdown 表示、翻译更新和渲染降级。图片凭证应与文字翻译 Provider 分开管理。Rust 可拥有云端 Provider 和结构归一化，但 Swift 仍负责捕获与明确授权。

### 隐私、成本和性能

- 图片上传必须逐次或通过明确设置授权，不能用“本地 OCR”文案掩盖。
- 需要限制尺寸、压缩、超时和计费提示。
- 取消必须终止上传并释放内存。
- 云端失败时回退 Vision，但不能假装保留了表格结构。

### 风险与未知

- 小截图的真实质量增益是否值得额外 TTFT。
- GLM-OCR 输出协议、模型版本、价格和地区可用性会变化。
- Markdown 结构并不等于可视布局，翻译后列宽和换行仍会变化。
- 双 Provider 凭证会显著增加设置复杂度。

### 进入开发的条件

1. 建立包含表格、代码块、混合语言、UI 截图的对比集。
2. 实测 Vision 与候选 GLM-OCR 的质量、TTFT、成本和失败率。
3. 通过图片上传披露和生命周期的产品决策。
4. 接受结构化内容数据契约的 ADR 更新。
5. 不与文档工作区同时开发，先选一个窄入口验证。

### 下一步

保持 BL-006 Deferred；未来优先做离线评测和 API 协议 spike。

## IDEA-004：万能文档翻译工作区

Status: Captured

Priority: Unranked

Source: 用户讨论

Created: 2026-08-05

Related: IDEA-003、IDEA-009

### 一句话描述

增加可显式打开的主界面，让用户输入 PDF、Office、图片和常见文档，完成多页结构解析、翻译、对照与导出。

### 用户问题与价值

瞬时翻译解决“当前看到的一小段”，但无法高效处理整篇论文、合同或演示文稿。文档工作区可以复用翻译核心，又需要完全不同的任务模型、持久化和版面策略。

### 与 Marla 核心的关系

它应是第二种使用模式，不应把主窗口重新变成瞬时翻译的必经入口。菜单栏/原位层保持轻量；用户明确拖入文档时才进入长期任务界面。

### 可能范围

- 第一阶段只读 PDF 文本层和图片 OCR，对照浏览，不导出回原格式。
- 第二阶段支持 DOCX/PPTX/XLSX 等结构化格式。
- 后续再考虑保版式导出、批处理、术语表和任务恢复。

### 主要依赖与风险

- 每种格式都有独立解析和导出语义，范围很容易失控。
- 多页任务需要队列、取消、进度、失败恢复和成本估算。
- 持久化文档会改变当前“不保存内容”的隐私模型。
- 表格、脚注、文本框、扫描页和公式需要结构化 OCR/文档解析。
- Swift/Rust 边界可能需要面向任务而非短会话的新协议。

### 进入开发的条件

1. 0.1.0 瞬时入口完成真实验收。
2. 选择第一个文件类型和最小成功标准，不能同时承诺“常见文档”。
3. 明确文件是否保存、保存多久、如何删除。
4. 确定输出是阅读对照还是保版式文件。
5. 建立独立产品规格和架构 ADR。

### 下一步

收集真实文档样本和用户最常见的第一个格式，再决定是否进入 Backlog。

## IDEA-005：用户可控术语表

Status: Captured

Priority: Unranked

Source: 上下文讨论

Created: 2026-08-05

Related: IDEA-001、ADR-0003

### 一句话描述

允许用户明确保存术语、固定译法、语言方向和适用领域，使连续翻译保持一致。

### 用户问题与价值

应用名、技术名词、人名和团队内部表达经常被模型改写。显式术语表比自动猜测更可控，也能成为上下文增强中置信度最高的证据。

### 可能形态

- 全局术语：所有应用生效。
- 应用/领域术语：只在 Terminal、代码或特定 Bundle ID 生效。
- 从结果卡片选择原文与译文后“记住此译法”。
- 仅手动维护，不自动学习；后续再评估建议模式。

### 隐私与数据

术语是持久用户数据，必须能查看、编辑、导出和彻底删除。默认只本地保存；未来同步需要新决策。不得自动把所有翻译历史转成术语。

### 风险与未知

- 术语在不同语境可能需要不同译法。
- 长术语表如何注入 Provider 而不显著增加 token 和延迟。
- 专用翻译模型是否支持结构化术语参数。
- 冲突、大小写、词形变化和语言方向规则如何表达。

### 进入开发的条件

先定义最小数据模型、优先级、编辑入口和删除语义；用一组可重复样本证明术语确实被 Provider 遵守。

### 下一步

与 IDEA-001 的隐私/提示词评测一起研究，但作为独立 Task 实现。

## IDEA-006：翻译历史、收藏与恢复

Status: Captured

Priority: Unranked

Source: 产品规划

Created: 2026-08-05

Related: `PRODUCT.md`

### 一句话描述

让用户在明确开启后查找最近翻译、收藏重要结果，并在崩溃或重启后恢复需要保留的工作。

### 用户问题与价值

瞬时卡片关闭后内容即消失，隐私最简单，但用户偶尔会误关重要译文或需要再次引用。历史可以减少重复请求，收藏可以支持长期资料。

### 可能方案

- 默认关闭的有限条数本地历史。
- 只保存用户明确“收藏”的条目，不自动记录。
- 会话内撤销关闭，退出后清空。
- 分别设置原文、译文、应用来源和截图缩略图的保存开关。

### 隐私和安全

这是对 0.1.0 数据生命周期的重大改变。必须明确加密、保留时长、搜索索引、删除、导出和截图是否永不保存。来源应用或窗口信息可能比译文本身更敏感。

### 风险与未知

- “默认历史”可能违背瞬时工具的信任模型。
- 本地数据库引入迁移、损坏恢复和数据清除测试。
- 云同步会引入账号、密钥和法规范围，不应与本地历史捆绑首发。

### 进入开发的条件

项目所有者先选择“仅收藏”“会话撤销”或“完整历史”中的最小形态，并接受新的隐私说明。0.1.0 继续不持久化原文、译文和截图。

### 下一步

保持 Captured，等待真实使用证明误关/查找是高频问题。

## IDEA-007：更可靠的 Force Touch 入口

Status: Exploring

Priority: Unranked

Source: 用户偏好

Created: 2026-08-05

Related: BL-004、IDEA-002

### 一句话描述

用户划词后重按触控板，触发与键盘快捷键相同的翻译意图，并显示附近卡片或未来原位覆盖层。

### 用户价值

划词动作本来就发生在触控板上，重按可以减少手移到键盘的成本，比悬停自动翻译更有明确意图，也不容易误触大量请求。

### 产品边界

- 它是入口，不是独立翻译模式。
- 默认关闭并标记实验。
- 键盘快捷键永远是可靠回退。
- 只使用公开 API；不为追求全局行为引入私有事件钩子。

### 需要验证

- 内置与外接触控板，不同 Force Click 设置。
- Safari、Terminal、TextEdit、Electron 应用是否能全局观察压力事件。
- 与查词、预览、拖动和源应用自身 Force Click 的冲突。
- 无选区、拖动选区和多指手势期间的误触率。

### 性能和隐私

全局监听不得持续采集文字；只有确认压力阈值并触发后才读取当前选区。事件监控不应明显增加空闲 CPU 或阻止系统睡眠。

### 进入开发的条件

完成 BL-004 的硬件/应用矩阵。若公共 API 无法达到可预测行为，接受移除实验开关，而不是把它变成发布阻塞项。

### 下一步

创建纯可行性 Task，记录成功率和冲突，不先优化视觉。

## IDEA-008：更多瞬时翻译入口

Status: Captured

Priority: Unranked

Source: 用户讨论

Created: 2026-08-05

Related: `PRODUCT.md`、`UX_PRINCIPLES.md`

### 一句话描述

在不打开传统主窗口、不后台监视内容的前提下，为不同工作流提供更多明确触发的翻译入口。

### 候选入口

| 候选 | 用户动作 | 价值 | 主要问题 |
| --- | --- | --- | --- |
| macOS Services | 右键服务菜单翻译选区 | 系统原生、权限路径不同 | 步骤较多，应用支持不一致 |
| 剪贴板显式翻译 | 快捷键翻译当前剪贴板 | 可兼容难读选区的应用 | 需避免误传旧的敏感剪贴板 |
| 拖拽到菜单栏图标 | 拖文字或图片 | 意图明确，适合图片 | 拖动成本较高，文件生命周期复杂 |
| 菜单栏快速粘贴 | 点击后直接粘贴 | 容易发现 | 比全局快捷键更打断 |
| Finder 文件 Quick Action | 对选中文件发起任务 | 文档入口自然 | 会跨入 IDEA-004 的大范围 |
| Spotlight/App Intent | 从系统搜索触发 | 系统整合 | 参数和结果呈现受平台限制 |

### 明确不优先

纯悬停自动翻译暂不优先：意图弱、误触多、可能持续读取屏幕，并且可以被“划词 + 快捷键/Force Touch + 原位呈现”的方案覆盖。

### 选择原则

- 用户必须明确表达一次翻译意图。
- 入口应复用统一 `TranslationIntent` 和结果卡片，不复制 Provider 逻辑。
- 新入口若需要读取或上传新类型数据，必须单独说明隐私边界。
- 先用真实频率证明价值，不追求入口数量。

### 进入开发的条件

从候选中一次只选择一个，写出比现有三个入口更适合的具体场景和可测成功标准，再创建 Task。

### 下一步

在日常试用 0.1.0 时记录“想翻译但现有三入口不顺手”的真实事件，而不是先实现候选列表。

## IDEA-009：本地 OCR / VLM 能力分档

Status: Captured

Priority: Unranked

Source: OCR 模型讨论

Created: 2026-08-05

Related: IDEA-003、IDEA-004、ADR-0002

### 一句话描述

未来按设备资源和任务复杂度提供 Vision、本地轻量结构模型、云端高质量模型等能力档位，而不是强制所有用户常驻一个中档模型。

### 背景判断

Marla 软件本体期望约 200MB，OCR 额外工作内存理想为 300–500MB，整体不超过 1GB。对于小截图，Vision 启动快、系统集成好；许多本地 VLM 模型即使权重小，运行时和峰值内存也可能超过预算，而且结构质量不一定值得。

### 候选档位

- **系统轻量档**：Vision，零额外模型包，纯文本/行序。
- **可下载本地增强档**：只在未来找到实测明显优于 Vision且满足内存的模型时提供。
- **云端结构档**：GLM-OCR 等，质量优先，需要上传披露。
- **文档专用档**：只在文档工作区启用，不让瞬时翻译承担常驻成本。

### 需要实测的指标

模型文件大小、冷启动、热启动、常驻内存、峰值内存、首结果时间、能耗、表格/代码/中英混排准确度，以及模型卸载后系统是否真正回收内存。不能只依据参数量推断。

### 风险与未知

- Core ML/MLX/ONNX 运行时的实际内存与权重大小差异很大。
- 非常驻模型的加载时间可能破坏瞬时体验；常驻又占用空闲预算。
- 自动选择档位会让用户难以理解图片是否上传。
- 模型许可、更新和 Apple Silicon 代际兼容增加发行复杂度。

### 进入开发的条件

必须有候选模型在目标 Mac 上的真实基准，并同时满足：相对 Vision 的明确质量增益、可接受冷启动、峰值低于 1GB 硬上限、可分发许可和清楚隐私语义。否则继续选择 Vision + 可选云端。

### 下一步

不把模型打进 0.1.0；文档工作区进入规划后再建立 benchmark Task。

## IDEA-010：多翻译 API 配置与窗口内切换

Status: Captured

Priority: Unranked

Source: 用户补充 + 当前 OpenAI-compatible / Qwen-MT 适配经验

Created: 2026-08-06

Updated: 2026-08-06

Related: `IMPLEMENTATION.md`、Rust translation provider

### 一句话描述

允许用户保存多个具名翻译 API 配置，并直接在弹出的翻译结果窗口中切换配置、使用同一份源文本重新翻译。

### 用户问题与价值

当前只配置一个 Base URL、模型和 Key，简单但切换成本高。用户可能同时拥有多个服务商、同一服务商的多个模型，或“快速低成本”“高质量”“本地代理”等不同配置。不同模型可能分别擅长短句、术语和长文；某个端点限流或结果不理想时，用户希望留在当前翻译窗口里立即换一个配置，而不是先关闭结果、打开设置、修改全局参数再重新触发翻译。

### 已明确的核心交互

- 设置中可以创建、命名、编辑、测试、排序和删除多个翻译配置。
- 每个配置至少包含显示名称、Base URL、模型名和独立的可选 API Key；未来的 Provider 专属能力另行决定。
- 用户可以指定默认配置，新的翻译会话先使用该配置。
- 划词、截图和快速输入的结果窗口都显示当前配置名称，并提供紧凑的配置切换入口。
- 在窗口中切换配置时，先取消当前进行中的请求，再复用同一份源文本和目标语言发起新请求。
- 截图翻译切换配置时不重新截图、不重新执行 Vision OCR，只重跑文字翻译。
- 切换是用户显式操作；不因为超时、限流或失败而静默把文本发送到另一家服务。

这个想法的首要目标是“多个配置 + 用户随时切换”，不是一开始就实现复杂的自动路由。

### 可能的后续形态

- 为划词、截图、快速输入或未来文档翻译设置不同默认配置。
- 允许临时切换只影响当前卡片，或提供“设为默认”的独立操作。
- 在保留同一源文本的前提下，对比两个配置产生的译文。
- 按语言、成本或能力建议配置，但仍由用户确认后切换。
- Provider capability 描述是否支持 system prompt、术语、上下文、图片和专用参数。

### 翻译窗口行为草案

- 配置选择器应显示用户定义的短名称，例如“Qwen 快速”“GPT 高质量”“本地代理”，避免在紧凑卡片中直接展示长 URL。
- 切换进行中请求时，旧请求必须遵守现有 request ID 隔离规则；迟到的 delta 不得写入新结果。
- 已完成译文如何处理尚未决定：可以直接替换，也可以在短时间内保留上一结果用于返回或比较。
- 配置无效、缺少 Key 或连接失败时，保留原文和已有译文，并提供打开该配置设置的操作。
- 配置切换控件不能破坏非激活卡片、稳定锚点和流式内容不跳动的现有体验原则。

### 架构影响

每个翻译配置需要稳定且不可由显示名称替代的配置 ID。Keychain 按配置 ID 保存多个凭证，非敏感字段和默认配置 ID 存入应用偏好；重命名配置不能丢失 Key。现有单配置数据需要一次可回滚的迁移。Rust 请求应收到当前会话选中的完整配置，并逐步使用明确的 Provider adapter/capability，而不是不断按模型名前缀堆条件。自定义 Header 和厂商专属参数涉及安全与 UI，需单独决策。

### 隐私、成本和错误语义

- 界面必须清楚显示本次文本发送到哪个端点。
- 自动 fallback 可能导致同一内容发送给第二家服务和重复计费，默认不应静默发生。
- 删除配置必须同步删除 Keychain 项。
- 连接测试不应把用户内容作为样本。
- 用户主动切换配置意味着同一源文本可能发送给多个服务；界面需要让这一结果可预期，但不应每次弹出打断式确认。

### 风险与未知

- “OpenAI-compatible”只覆盖表面协议，各家 SSE、错误和提示词规则仍不同。
- 选项过多会让设置变成开发者控制台，损害产品简洁度。
- 如何迁移当前单配置而不丢 Keychain 凭证。
- 紧凑结果卡片中的配置选择器如何保持易用，又不挤压译文和主要操作。
- 切换后是替换译文、保留上一版，还是进入显式多模型对比模式。
- 默认配置是全局一个，还是允许每个入口分别记忆。

### 进入开发的条件

1. 确认首期只做手动切换，不包含自动故障转移或智能路由。
2. 定义配置数据模型、稳定 ID、Keychain 命名和当前单配置迁移方式。
3. 决定窗口切换后如何处理已经完成的旧译文。
4. 为进行中切换、失败配置、删除默认配置和迟到事件建立验收标准。
5. 从本想法提升到 Backlog 后，再拆成“多配置存储/设置”和“结果窗口切换”两个可独立验证的 Task。

### 下一步

保持 `Captured`，不改变 0.1.0 单端点合同。项目所有者决定排期时，先确认旧译文处理和默认配置作用域，再提升到 Backlog。
